# M3 on B200

Run the preflight before launching distributed training. It checks the Python
imports, PyTorch CUDA architecture, BF16 support, the nvdiffrast CUDA context,
and the exact checkpoint copy path:

```bash
python scripts/check_m3_environment.py \
  --device cuda:0 \
  --output-dir /path/to/training/output \
  --checkpoint-staging-dir /path/on/local-or-pfs/checkpoint-staging
```

Use Python 3.11, PyTorch 2.7 or newer built for CUDA 12.8, and a matching NVIDIA
driver. A generic `torch>=2.4` environment is insufficient for B200: the wheel
must list the GPU's `sm_100` architecture. Install `nvdiffrast` in that same
environment and let the preflight create a CUDA raster context before an
eight-GPU launch.

The exact stack checked in the current environment is recorded in
`requirements/m3-b200.txt`, including immutable Git commits for utils3d and
nvdiffrast. Build a fresh Python 3.11 environment on the target machine instead
of copying this repository's `.venv`, because compiled CUDA extensions and
absolute interpreter paths are machine-specific.

Do not serialize PyTorch or safetensors objects directly onto an OSS FUSE mount.
`train_renderer.py` now serializes and verifies each checkpoint under
`--checkpoint-staging-dir`, then copies the completed ordinary file to the
output directory. The default staging root is `$PLOT_CHECKPOINT_STAGING_DIR`
or the system temporary directory. Set it explicitly to node-local SSD or PFS
on a cluster. With the default `--checkpoint-errors warn`, a failed copy is
written to `checkpoint_failures.jsonl` and training continues; use `raise` when
a missing checkpoint must terminate a run.

The preflight does not reserve training memory and cannot predict the batch size
that fits. Start the first B200 job with `--context-frames 9 --batch-size 1`,
confirm one forward/backward and checkpoint, then switch to the 65-frame recipe.
After that smoke check, `train_scripts/recipes/m3/train_m3_b200_8gpu.sh` runs the
formal 65-frame job and its five W&B visualization probes.
